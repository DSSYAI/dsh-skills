# 陌生项目逆向与改造工作流

面向"接手一个不熟悉的软件/项目，读懂它，然后安全地改它"的可复用流程。
与具体语言、框架、项目结构无关：**每一阶段的动作都是"去哪里找证据"，而不是"按某框架的惯例猜"。**

核心两条原则，后文所有规则都由它们推导出来：

1. **先确认，再修改。** 没有证据的结论就是假设；假设不能作为改动的依据。
2. **用产物验证，不用推理验证。** "代码这么写所以应该生效"不是验证；"构建产物里确实存在这段逻辑"才是。

---

## 1. 阶段总览

| 阶段 | 名称 | 关键产出 | 出口条件（不满足就不进入下一阶段） |
|---|---|---|---|
| S0 | 环境侦察 | 工具链 + 环境脚本 + 版本表 + 环境坑清单 | 能用项目自己的入口跑通一次"零改动构建/运行" |
| S1 | 结构侦察 | 结构地图（入口、核心目录、关键文件、构建方式） | 能回答"改这个功能该去哪个目录找" |
| S2 | 全量审计 | 候选改动清单（含难度、影响面、未验证标注） | 需求方能在清单上勾选范围 |
| S3 | 目标定位 | 目标功能的文件与符号位置 | 已**读到**目标逻辑源码，而非猜它大概在哪 |
| S4 | 机制求证 | 带证据的机制结论 | 每个"它会这样/不会这样"的说法都附了证据来源 |
| S5 | 改动规划 | 改动方案 + 受影响引用枚举 + 验证方案 | 通过 §7 的"修改闸门"五问 |
| S6 | 小范围实施 | 批次化提交 | 每批次自成一个可解释、可回退的单元 |
| S7 | 构建与验证 | 验证记录（基线对比 + 产物校验） | 静态检查、测试、构建、产物校验全部有结论 |
| S8 | 问题排查 | 根因 + 证据 + 修复 + 回归结论 | 能说清"为什么以前坏、为什么现在好" |
| S9 | 交付与记录 | 单一交付位置 + 复现文档 + 改动台账 | 他人按文档能从零复现 |

## 2. S0 环境侦察

**目标：在动任何代码之前，先能把它原样跑起来。**

### 2.1 从项目自己的文件里读工具链需求，不要凭经验猜

按优先级依次查：

| 找什么 | 常见载体 |
|---|---|
| 语言/运行时版本 | 版本文件、`tool-versions`、`go.mod`、`package.json engines`、`environment:` 段 |
| 构建工具与版本 | 包装器脚本与配置、`gradle-wrapper.properties`、锁文件、`Dockerfile` |
| 项目锁定的工具链 | **子模块 / 固定版本的 SDK / toolchain 声明**（这一条最容易被忽略，见 §11.4） |
| 平台 SDK 与原生工具链 | 平台构建配置文件（NDK/SDK/编译器等） |
| 构建入口 | CI 配置、`Makefile`、脚本目录、README 的构建章节 |
| **项目的"完成定义"** | CI 工作流文件：它跑哪些命令，就是"改了之后必须全绿"的清单 |

> 一定要读 CI 配置。它通常同时给出：构建入口、测试命令、静态检查命令、格式化检查命令、以及被跳过的步骤（跳过往往暗示已知的坏味道）。

### 2.2 环境落地

- 每个工具链装在**一个可整体搬走/删除的根目录**下，不要散落。
- 写一个**可被 source 的环境脚本**（设变量 + 改 PATH），并额外提供一份给非交互 shell 的等价版本。
- **环境变量必须每次命令重新加载**：子进程/新终端继承的往往是过期环境，"我明明设过了"是最常见的假象之一。
- 记一张**版本表**（组件 / 版本 / 路径），放进交付文档。这既是复现依据，也是排查"是不是版本不一致"的第一手资料。

### 2.3 先跑通一次零改动构建

在改任何东西之前，必须完成一次"原样构建成功"。

- 记录**基线**：静态检查结果、测试通过/失败数、构建产物大小与校验和。
- **把预先存在的失败逐个归因**（代码缺陷 / 平台差异 / 环境缺失 / 已知上游问题）。归因之后基线才能当信号用；不归因的基线只会让你在改动后无法区分"我弄坏的"和"本来就坏的"。
- 这是整个流程里最省时间的一步：没有基线，后面每一次失败都要重新调查。

### 2.4 受限网络/受限机器的处置套路

当依赖下载不稳定时，按顺序尝试（每一步都要记录，因为它们都改变环境）：

1. **镜像写进仓库配置**（覆盖面最大：项目自身、子项目、插件各自的仓库声明）。注意有些构建系统**不继承**根项目的仓库配置，插件模块会自己声明仓库 —— 需要分别处理。
2. **仓库外的全局注入**（构建工具的 init/全局配置目录），适合"不想污染仓库"的改动。但要注意：注入位置不对会破坏某些插件的解析（比如把仓库塞进插件管理层可能让框架自己的插件加载器失败）——一次只加一处，加完立刻验证。
3. **独立下载器**：并行分块 + 断点续传，绕过单连接限速。
4. **停滞检测 + 自动重试**:很多构建工具**增量缓存**已完成的部分，所以"卡死就杀掉重来"通常每轮都有净推进，比一直等更有效。判断卡死的标准应该是"日志和缓存目录**都**停止变化"，而不是只看日志。

### 2.5 环境级改动的记录规则

只要改了**仓库之外**的东西（缓存里的依赖、全局配置），就必须同时写下**撤销方式**。
判断标准：将来别人（或你自己）在另一台机器上，需要知道"这台机器和干净环境差在哪"。

## 3. S1 结构侦察

### 3.1 先量化，再阅读

用文件计数/体积统计代替"随便翻几个文件"。一张按目录分组的统计表能立刻告诉你：

- 哪些目录是**代码**，哪些是**生成物/资源/素材**（后者通常巨大且与逻辑无关）
- 核心代码的实际规模（往往比仓库总大小小 1~2 个数量级）
- 哪些目录可以整体忽略

### 3.2 读项目的自述性文件（按性价比排序）

1. CI 配置 —— "完成定义"与真实构建入口
2. 依赖清单 —— 技术栈、能力边界、可删除候选
3. 项目自己的脚本目录 —— 维护者平时怎么做事，比 README 更真实
4. **项目自己的变体/补丁机制**（若有）—— 见下
5. 静态检查配置 —— 编码约束，避免改出"能跑但不合规"的代码
6. README / CONTRIBUTING —— 最后看，信息密度最低

### 3.3 找"变体机制"：最高价值的一步

成熟项目常常已经在做"同一套源码产出多种构建"：补丁目录、特性开关、构建变体、条件编译、平台分支。

**这是你改造它的现成通道。** 找到它意味着：

- 你不需要发明一套新的改造机制，沿用它的约定即可（补丁放哪、什么时候应用、如何撤销）
- 你能学到维护者认可的改动边界
- 你还能看到它对"临时改动"的提示（例如明确写了"这个脚本只应在 CI 运行，误跑了用某命令撤销"）

### 3.4 确定入口

| 层次 | 找法 |
|---|---|
| 程序入口 | 标准入口符号（`main` 等）、平台入口文件 |
| 路由/导航入口 | 路由表、页面注册处 |
| 平台原生入口 | 平台清单/入口类（权限、深链、后台任务、原生通道都在这里） |
| 数据入口 | 存储层、序列化层、文件管理 |
| 事件入口 | 全局事件总线、原生↔宿主的通道名 |

**平台清单文件是必读项**：它是"仓库里声明了什么"与"最终产物里真的有什么"之间的桥梁，也是后面删依赖时最容易踩雷的地方（§10.4）。

## 4. S2 全量审计（先出清单，再动刀）

**不要直接开改。先产出一份"可以改什么"的清单，让需求方裁范围。**

清单里每一项至少给：

- 模块名与**主要文件（附行数）**
- 用户可见的效果（"删了以后用户会看到什么变化"）
- **难度**（低/中/高）与**牵连面**（会影响哪些其它模块、数据流、测试）
- 依赖它的其他模块（枚举引用点，而不是"应该没人用"）

两条纪律：

1. **不确定就标注"未验证"。** 尤其是"删掉会变小/变快"这类结论，没有实测就不要给数字。标注不确定性是专业行为，不是示弱。
2. **区分"能删"和"该删"。** 给出建议但把决定权留给需求方 —— 他们才知道自己的使用习惯。

产出这份清单的收益：需求方可以打包选择（"要 A1+A2，不要 A3"），避免你按自己的猜测做了大量无用功。

## 5. S3 目标定位（线索目录）

从"完全不了解"到"找到那几行代码"，靠的是**从线索出发的双向夹逼**。

### 5.1 线索类型（按命中率排序）

| 线索 | 例子 | 常用手段 |
|---|---|---|
| **用户可见字符串** | 界面文案、错误信息、按钮文字 | 全文检索（命中率最高） |
| **文件名/目录名** | 功能名往往就是文件名 | 路径匹配 |
| **配置键/偏好键** | 设置项的名字 | 全文检索 |
| **路由/API/端点** | URL 片段、路由常量 | 全文检索 |
| **事件/通道名** | 原生与宿主之间的通道标识 | 全文检索（跨语言定位的利器） |
| **平台清单声明** | 权限、组件、意图过滤器 | 读清单 |
| **依赖名** | 功能由某个库提供 | 读依赖清单 → 再读该库源码 |
| **测试名** | 测试的描述往往就是功能名 | 检索测试目录 |
| **资源名** | 图标、模板、字体 | 资源清单 |

多语言项目注意：界面文案可能被抽取到翻译文件里，此时**先去翻译文件里找到键，再用键去检索代码**。

### 5.2 双向夹逼

- **自上而下**：从入口/路由表 → 页面组件 → 具体逻辑。
- **自下而上**：从线索字符串所在的行 → 它被谁调用 → 一路向上到入口。

两个方向在本子上会合的位置，就是"这个功能真正被串起来的地方"。**两条路都能到达同一处**，说明定位可信；只走通一条，说明还有没看到的分支。

### 5.3 判断哪些代码是真正的核心逻辑

核心逻辑的特征：

- 被多处引用（引用点数量是最客观的指标）
- 直接读写持久化数据
- 出现在数据流的关键节点（序列化/反序列化、状态变更）
- 改动它会连带影响测试与其它模块

外围代码的特征：只被一处引用、纯展示、可替换的实现细节。

**改动应当尽量落在外围，把核心逻辑的接口当作边界。** 必须动核心时，优先"扩展"而不是"改写"（§8）。

## 6. S4 机制求证（反猜测）

以下三类问题**必须外部求证，禁止凭直觉**。它们的共同点是"你的直觉来自别的项目，而这里可能不一样"。

| 类型 | 为什么危险 | 求证渠道（按可靠性排序） |
|---|---|---|
| 第三方依赖的真实行为 | 文档滞后、字段名骗人、平台实现不一致 | ① 本地依赖缓存里的**源码** → ② 官方文档/API 页 → ③ 自己写最小实验 |
| 框架/运行时的默认值 | 默认值往往与预期相反，且常常不写在文档显眼处 | ① **框架 SDK 源码**（本地就有）→ ② 官方文档 |
| 平台/构建系统行为 | 各平台差异大，构建系统行为随版本变化 | ① 构建产物 → ② 官方文档 → ③ 最小复现工程 |

### 6.1 三个高价值习惯

1. **本地依赖缓存里就有源码。** 绝大多数包管理器把依赖源码解压在本地。直接读它，比搜索快且准（版本一定对得上）。
2. **框架 SDK 也在本地。** 需要确认某个 API 是否可空、某个默认值是真是假时，去读 SDK 源码，不要靠记忆。
3. **"能力标志"可能是假的。** 库自述的能力探测字段可能没有正确填充（例如某平台的实现完整、但探测字段恒为假）。**结论要以实现为准，而不是以自述字段为准。**

### 6.2 产出要求

每个机制结论都要写成一句"可反驳的断言 + 证据来源"，例如：

> 【已确认】X 在 A 平台默认开启，依据：SDK 源码 `path:line`，其判定函数在配置缺失时返回真。

不能写成"应该是开启的"。**"应该"是红灯词。**

## 7. 修改闸门：什么时候可以从"分析"切到"修改"

对**你即将改的那一处**，能回答全部五问才动手：

| # | 问题 | 不合格的表现 |
|---|---|---|
| 1 | 逻辑在哪个文件哪几个符号里？ | "大概在 xxx 目录" |
| 2 | 谁调用它、它调用谁？ | 只看到一个方向的调用 |
| 3 | 改了会影响谁？把引用**枚举**出来了吗？ | "应该没人用" / "影响不大" |
| 4 | 怎么知道它生效了？有无**可观察信号**？ | "跑一下看看" |
| 5 | 怎么知道没弄坏别的？基线在哪？ | 没有改动前的通过/失败记录 |

不满足时**继续分析**，不要用"先改改看"来替代分析。经验上，这一闸门拦下的返工远多于它耽误的时间。

## 8. S5→S6 改动规划与实施

### 8.1 五个"小范围改动"手法

| 手法 | 说明 |
|---|---|
| **复用既有管线** | 新功能优先接到项目已有的通路（某个导入/导出/渲染流程）上，而不是新写一条。省下的不只是代码量，还有边界情况。 |
| **只加可选参数** | 扩展函数时加**可选命名参数**，不动既有签名。这样所有既有调用方（包括测试）都不用改。 |
| **把新逻辑限制在入口处** | 需要"只处理一部分"时（例如只处理某个区间/子集），在入口处把输入裁剪好，再交给原有逻辑；原函数体一行不改，diff 最小。 |
| **不合并"看起来一样"的规则** | 两处相似但**行为不同**的规则（例如"去掉末尾空项"在 A 处只去一个、在 B 处去全部）**绝对不要合并**。合并 = 悄悄改掉其中一处的行为。 |
| **单一真源** | 同一条判定规则被多处需要时，抽成一个函数，让所有调用方都调它，避免多处实现漂移。 |

### 8.2 与既有架构的关系

- 遵循既有分层与命名，新代码放进项目**已经存在**的同类目录，而不是新建一套体系。
- 复用既有的对话框/组件/状态管理模式，不要引入第二种风格。
- 遵守项目的静态检查规则；改完跑一遍项目的检查命令。

### 8.3 出处标记：让改动以后找得到

用项目**已有**的注释风格，给自己新增/修改的代码加统一标记。例如在人类语言文案、新增类、新增函数的注释里带上同一句前缀。

收益：

- 后续维护时一个检索就能列出全部改动点
- 与上游同步（rebase/升级）时能快速识别冲突来源
- 与项目原有代码在阅读时一眼可分

**标记要在开工前就定好并全程一致**，事后补标记等于没有标记。

### 8.4 批次化提交

- 一个**自洽的批次**一个提交：要么"一个删除主题"，要么"一组相关功能"。
- 提交信息写**根因与理由**，不只写"改了什么"。以后回看时，理由比 diff 值钱。
- 把"顺手修的测试断言""gitignore 调整""事故修复"分成独立提交 —— 它们各自的回退语义不同。
- 每个批次结束时工作区应干净，并且能说清"这个提交之后，哪些行为变了、哪些绝对没变"。

## 9. S7 构建与验证

### 9.1 验证阶梯（逐级上升，不要跳级）

```
静态检查  →  单元/集成测试  →  构建  →  产物校验  →  真实运行
```

每一级都要**和基线对比**，而不是只看"这次是绿的"。

### 9.2 产物校验清单

**关键认知：你改的是源码，用户用的是产物。两者之间隔着一个构建系统，而构建系统会合并、裁剪、重命名、注入。**

| 项目 | 怎么查 | 常见坑 |
|---|---|---|
| 声明的组件是否都存在 | 把产物里的组件清单与产物内容逐一对齐 | **缺失的声明会在启动时致命**（§10.4） |
| 合并后的清单/配置 | 读**构建中间产物里的合并结果**，不要读源码里的原始文件 | 源码清单和最终清单可以差很多 |
| 代码/资源真的进包了吗 | 在产物里检索你新加的**标识符**或**字符串** | 字符串编码陷阱（§9.4） |
| 平台/架构正确 | 枚举产物里的平台分支/ABI 目录 | 构建出非目标平台的包 |
| 签名/完整性 | 用平台工具校验签名 | 签名不一致 → 无法覆盖安装 |
| 产物新鲜度 | 产物时间戳晚于全部源码时间戳 | 拿到旧产物还以为是新的 |

### 9.3 "看起来能跑" vs "真的生效"——怎么区分

以下情况**都算没验证**：

- 程序启动了、界面出来了，但你改的功能没被**主动触发**过一次
- 功能触发了，但你没有**检查它产生的数据/文件/副作用**
- 你只看了"没报错"，没看"结果对不对"
- 你验证的是**旧产物**（没重新构建，或构建产物没被替换到运行位置）

正确做法：为每个改动点写一条**可观察的验收动作 + 可观察的预期结果**，写进交付文档让使用者逐条勾。例如"选第 2~4 页导出 → 产物应当只有 3 页，且内容依次对应第 2、3、4 页"，而不是"导出功能正常"。

### 9.4 字符串/符号检索的假阴性陷阱

在产物里搜自己新加的字符串，是确认"代码真的进包了"的廉价手段，但有编码陷阱：

- **非 ASCII 文本在编译型产物里常以 UTF-16 存储**（而非 UTF-8）。按 UTF-8 搜中文会得到假阴性。
- 静态编译的产物可能把字符串放进制品表、常量池、资源包，位置不固定。
- 先搜一个**必然存在的 ASCII 标识符**（你新加的函数名）校准方法；再用正确的编码搜用户可见文案。

**若两种编码都搜不到，那就是真的没进包**——不要解释成"可能被优化掉了"。

## 10. S8 问题排查工作流

### 10.1 七步循环

```
现象 → 收集证据 → 缩小范围 → 提出假设 → 验证假设 → 修改 → 再验证（回到第一步）
```

每步的纪律：

1. **现象**：只写观察到的，不写解释。"点图标立刻闪退"而不是"大概是初始化崩了"。
2. **收集证据**：日志、堆栈、产物状态、能稳定复现的最小步骤。**先要可复现，再谈修复。**
3. **缩小范围**：二分/隔离。改动前是否正常？哪个提交引入的？哪个平台/架构独有？把问题从业务里摘出来单独复现。
4. **假设**：必须是**可证伪**的句子。"X 类的声明还在但类不存在，所以进程启动时抛异常"——可以验证。
5. **验证**：用证据验证，不要靠"改了以后好像好了"。**一次只改一个变量。**
6. **修改**：改根因，不是改症状（抑制日志、加 try/catch 都是改症状）。
7. **再验证**：原现象消失；同时确认没有引入新的失败（对比基线）。

### 10.2 特别有效的几个方法

| 方法 | 用法 |
|---|---|
| **声明 vs 产物的差集** | 把"配置/清单/依赖图里声明的集合"与"产物里实际存在的集合"求差集。**缺的、多的，都是线索。** 这个方法在本类改造中命中率极高。 |
| **依赖图/构建图** | 用构建系统自己的命令导出依赖树，看清"谁把谁带进来了"。替代"凭包名猜"。 |
| **改动前后差分** | 对同一命令的两次输出做 diff（配置、依赖树、产物清单）。比盯着一份输出看有效得多。 |
| **历史二分** | 有版本控制时，用提交历史找引入点；不要逐行猜。 |
| **先暂停无关进程** | 排查构建/工具链问题时，先确认没有残留进程占着资源或锁。 |
| **把结论写下来** | 每一步的结论（含"已排除"）都写进一个持久文件。避免重复探索，也避免推翻已验证的结论。 |

### 10.3 归因四分表：代码 / 依赖 / 环境 / 配置

| 类别 | 典型信号 | 处置方向 |
|---|---|---|
| **代码问题** | 逻辑错误、空引用、断言失败；复现稳定且与平台无关 | 改代码 |
| **依赖问题** | 版本冲突、"包不存在"、类/符号找不到、间接依赖拖入多余树 | 读依赖图，明确升级/降级/排除，而不是撞运气 |
| **环境问题** | 缺工具、缺 SDK、路径不对、网络失败、权限拒绝；换台机器就好了 | 补环境并**记录到环境脚本与版本表** |
| **配置问题** | 配置项写错、注入位置不对、格式/编码问题；同一份代码换个配置就好 | 改配置，一次只改一处 |

**判据**：如果"换环境/换配置"能改变结果，那就不是代码问题。先分类再修，避免在错误的方向上连续返工。

### 10.4 本类改造最典型的事故：删了依赖，声明还在

**删掉一个依赖/插件时，必须同步审计所有手工声明的引用。**

平台清单、构建配置、注册文件、原生入口里常有**手工写死**的组件/服务/权限声明，它们不会随依赖消失。而某些平台会在进程启动、业务代码运行之前就实例化所有声明的组件 —— 缺失的实现会导致**启动即崩，界面完全不出现**。

处置套路：

1. 删依赖后，列出**全部**声明类组件（组件/服务/接收器/权限/初始化项）。
2. **逐个验证**对应的实现是否存在于产物中。
3. 不要只修找到的那一个 —— **做全量核对**，排除同类地雷。
4. 把这条教训写进交付文档。

## 11. 依赖与环境管理

### 11.1 依赖四分法

接手项目后会引入的依赖分四类，**管理方式完全不同**：

| 类别 | 举例 | 是否进交付 | 记录方式 |
|---|---|---|---|
| **原项目依赖** | 项目自己声明的库 | 是 | 只记录"我删/加了哪些、为什么" |
| **分析工具依赖** | 反编译、产物检查、签名校验等 | 否 | 单独记录，说明"仅本地分析用" |
| **开发依赖** | 测试、格式化、代码生成 | 视情况 | 记录，并注明是否影响交付产物 |
| **临时依赖** | 一次性脚本、临时环境 | 否 | **用完即删**，并在环境文档里留一行"曾经装过什么、怎么删" |

**关键区分：直接影响交付产物的依赖 vs 只影响你分析过程的依赖。** 前者必须可复现，后者不该混进交付说明。

### 11.2 每个依赖都要能回答四个问题

1. **为什么需要它**（缺了会怎样）
2. **版本是多少**（精确版本，不是"最新"）
3. **装在哪里**（是否在仓库外）
4. **怎么撤掉**（卸载/回滚命令）

### 11.3 判断哪些可以清理

可以安全清理的信号：

- 只被一次性脚本使用，脚本已不再需要
- 功能已被内置能力替代
- 是某个已删除依赖的间接残留（**依赖图能直接看出这个**）

清理前先确认没有引用点（用项目自己的检索/构建命令验证），清理后重跑一次构建与静态检查。

### 11.4 工具链版本漂移：最容易误判的一类"问题"

项目可能**锁定**自己的工具链（子模块、固定版本 SDK、toolchain 文件）。而你可能因为方便，另外装了一个"满足版本约束"的版本。

后果：项目自带的某些检查（尤其**格式化检查**）会对**你没有改过的文件**报出大量差异。这时：

- **不要盲目服从格式化工具** —— 那会产生一大堆与你的改动无关的 diff，淹没真正的改动。
- 先确认本机工具版本与项目锁定的是否一致。
- 处置：要么换成项目锁定的版本，要么保持与周围代码一致的风格，并在交付文档里说明原因。

**这类"幻影差异"是环境问题，不是代码问题**（§10.3）。

### 11.5 让环境可复现

交付时至少给：

- 环境脚本（变量 + PATH，可 source）
- **版本表**（组件 / 版本 / 路径）
- **已知环境坑清单**（每条写：症状 → 根因 → 已采用的处置 → 撤销方式）
- 构建入口与**正确的调用方式**（以及"不要用某个底层命令代替"的说明，如果存在这种陷阱）

判断"这个依赖值不值得装"的实用标准：**它是否会让"从零到能构建"这件事，在另一台机器上无法靠文档完成。** 会，就必须记录。

## 12. S9 交付与记录

### 12.1 单一交付位置

产物只放**一个**地方，并明确告知路径与校验和。多处副本会导致"我装的到底是哪个包"。

同时记录：精确的文件名、大小、校验和、构建命令、以及"它是从哪个提交构建出来的"。

### 12.2 交付文档必备章节

| 章节 | 内容 |
|---|---|
| 产物 | 唯一路径、大小、校验和、构建命令、签名信息 |
| 环境 | 版本表、环境脚本用法、工具链位置 |
| 改动记录 | **按批次**列出改了什么、为什么；关联提交 |
| 机制说明 | 关键实现点的原理（为什么这么做，而不是只写做了什么） |
| 事故复盘 | 症状 → 根因 → 证据 → 修复 → 教训（**价值最高的章节**） |
| 已知限制 | 未验证的部分、平台差异、刻意的取舍 |
| **使用侧验收清单** | 逐条"操作 → 预期现象"，供使用者勾选 |
| 重新构建步骤 | 从零到产物的完整命令序列 |

### 12.3 诚实地标注边界

- 明确写"**只做了静态校验，未在真实环境运行过**"，不要用"已验证"含糊带过。
- 明确写"哪些平台保持原样、可能已经不可用"。
- 明确写"哪些是有意为之的行为变更"（尤其是顺手改掉的小毛病），让需求方能否决。
- 已知的、无法消除的小副作用（例如某个操作的附带影响）也写进去，避免使用者误判为 bug。

### 12.4 收尾自检

- 工作区干净，无游离改动、无遗留的临时/失败产物
- 产物时间戳晚于全部源码
- 交付位置只有预期的那几份文件
- 交付文档里的数字（大小、校验和、测试统计）都是**实测**的

## 13. 反模式速查

| 反模式 | 后果 | 对策 |
|---|---|---|
| 没跑通基线就开始改 | 无法区分"我弄坏的"和"本来就坏的" | 先零改动构建 + 失败归因 |
| 凭记忆/惯例推断库与框架行为 | 结论错，改动方向错 | 读本地源码或官方文档（§6） |
| "应该没人用" | 漏改引用，运行时才炸 | 枚举引用点 |
| 把相似的规则合并 | 悄悄改掉一处行为 | 保持两处独立（§8.1） |
| 改了源码就当改完 | 产物没重建/没替换，验证的是旧包 | 校验产物新鲜度（§9.2） |
| 只看"没报错" | 功能其实没生效 | 可观察的验收动作 + 预期结果 |
| 用推理代替产物检查 | 漏掉合并/裁剪/注入造成的问题 | 求"声明 vs 产物"的差集（§10.2） |
| 删依赖不查手工声明 | 启动即崩 | 全量核对声明组件（§10.4） |
| 环境改动不写撤销方式 | 别人无法复现、无法回退 | 每条环境改动配一行撤销说明 |
| 盲目服从格式化/检查工具 | 无关 diff 淹没真实改动 | 先核对工具链版本（§11.4） |
| 交付多份产物 | 装错包 | 单一位置 + 校验和 |
| 只写"做了什么" | 以后没人知道为什么 | 提交信息与文档写根因与理由 |

## 14. 最小检查清单

**动手前**
- [ ] 零改动构建跑通，基线（静态检查/测试/产物）已记录
- [ ] 预先存在的失败已逐个归因
- [ ] 需求范围已确认（有审计清单，需求方已勾选）
- [ ] 目标逻辑**已读到源码**，调用链双向走通
- [ ] 引用点已枚举
- [ ] §7 五问全部能回答

**动手时**
- [ ] 出处标记已统一
- [ ] 只加可选参数 / 复用既有管线 / 不合并相似规则
- [ ] 遵守项目静态检查规则
- [ ] 按批次提交，信息含根因

**完成后**
- [ ] 静态检查干净
- [ ] 测试与基线对比，无新增失败
- [ ] 构建成功，产物为预期平台/架构
- [ ] 产物校验：声明组件齐全、新代码/文案确实进包、签名有效、时间戳新鲜
- [ ] 验收清单逐条可操作
- [ ] 交付文档写完（含事故复盘与已知限制）
- [ ] 工作区干净，交付位置只有预期文件
